# V2 学习效果契约

## 目标

让正在使用 Agent 开发软件的初学者，通过接近真实项目的任务，逐步获得以下能力：

1. 看懂任务目前处于需求、方案、实现还是验证阶段。
2. 沿前端、API、后端和数据库追踪数据与故障。
3. 阅读 Git 状态、代码 diff、日志、测试结果和报错堆栈。
4. 向 Agent 提供可执行的需求与有效上下文。
5. 判断 Agent 的方案、实现和验收证据是否可信。

产品不得用“完成页面”“看过解释”或“选中明显正确答案”冒充能力提升。

## V1 失败清单

| 编号 | 已证实问题              | 为什么影响学习                 | V2 必须提供的证据                                     |
| ---- | ----------------------- | ------------------------------ | ----------------------------------------------------- |
| F-01 | 诊断依赖 1～5 自评      | 测到的是信心，不是实际能力     | 用户必须处理未知项目材料；结论引用具体作答证据        |
| F-02 | 每关只有一道单选题      | 可凭常识、措辞或排除法猜中     | 至少包含分析、操作、解释三种证据                      |
| F-03 | 错误选项明显荒谬        | 无法区分“真正理解”和“会做题”   | 干扰项必须来自真实常见误判，且都有局部合理性          |
| F-04 | 答对立即提升技能等级    | 一次识别不能证明独立操作       | 等级变化必须满足多证据门槛；单次完成只记录证据        |
| F-05 | 没有延迟复测和变式      | 无法证明记住或迁移             | 24 小时后安排同原理、不同表象的复测                   |
| F-06 | 只保存最终 XP           | 无法知道是否靠提示、重试或猜测 | 保存尝试、提示、耗时、答案、解释和验证结果            |
| F-07 | localStorage 是唯一存储 | 缓存清除即丢失，记录不可审计   | 使用本地数据库作为事实源，localStorage 仅保存界面偏好 |
| F-08 | 验收只覆盖 UI 和构建    | “软件可用”不等于“用户学会”     | 验收包含真实用户前测、任务、迁移题和复盘质量          |

## 能力等级

任何技能等级都不能由 XP 直接决定。XP 只代表投入，能力等级代表证据。

| 等级        | 能力含义                         | 最低证据要求                                       |
| ----------- | -------------------------------- | -------------------------------------------------- |
| L0 未诊断   | 没有足够证据                     | 尚未完成基线任务                                   |
| L1 识别     | 能在材料中找到相关概念           | 在无引导情境中正确识别 2 次                        |
| L2 引导完成 | 在提示下能完成标准任务           | 完成操作证据 2 次；提示次数被记录                  |
| L3 独立完成 | 能独立完成标准任务并解释原因     | 两个不同场景通过；至少一次零提示；解释覆盖关键因果 |
| L4 处理异常 | 能发现边界、失败路径和风险       | 成功路径与至少两个失败路径均被正确处理             |
| L5 审查设计 | 能比较方案、指出权衡并验收 Agent | 对真实 diff/方案作出有依据的审查，且迁移任务通过   |

## 单个关卡的证据结构

每个正式关卡必须按以下顺序运行：

1. **任务委托**：给出真实需求、现状和限制，不先讲知识。
2. **基线判断**：用户说明先检查什么以及为什么；此时禁止提示。
3. **材料调查**：查看精简但一致的代码、日志、网络请求、数据库或 Git 证据。
4. **实际操作**：排序排查步骤、标记相关文件/行、补充需求、修改沙盒代码或运行允许的命令。
5. **解释因果**：用自己的话说明问题如何产生、为什么方案有效。
6. **自动验证**：运行与任务匹配的测试或确定性规则；不能只依赖关键词。
7. **反馈与提示**：先指出证据缺口，再给分级提示，最后才展示参考方案。
8. **变式复测**：换业务名、数据或故障表象，验证是否掌握同一原理。
9. **证据入库**：保存原始作答、提示、结果和评分理由。

## 评分原则

- 正确结果但无法解释：最多记为 L2 证据。
- 使用完整答案提示后通过：记录完成，但不能用于晋级 L3。
- 猜中单选：只记识别证据，不提升能力等级。
- 自动测试通过：证明行为正确，不自动证明用户理解。
- 自由回答：先用明确 rubric 展示缺少哪些因果点；AI 评分未来只能辅助，不能作为唯一裁判。
- 用户可查看“为什么系统认为我是这个等级”并纠正事实性记录。

## 首个真实项目场景：画布保存成功但刷新丢失

### 为什么选它

它同时覆盖前端状态、HTTP、API、后端路由、数据库和验收证据，是常见且可迁移的真实故障；又与用户熟悉的画板业务接近，但使用独立沙盒，不读取 CanvasStorm。

### 场景材料

提供一个可运行的最小全栈项目：

- React 画布列表与保存按钮；
- Node API；
- SQLite 数据库；
- Network 请求记录；
- 后端日志；
- 数据库查询结果；
- 相关测试；
- 一份包含局部正确但验收不足的 Agent 交付说明。

种子故障：前端在请求返回前就显示“保存成功”，后端缺少持久化调用，因此内存中可见、刷新后消失。故障必须由运行和测试证明，不能只写在题干里。

### 任务阶段

1. 不看提示，写出前三个检查动作及理由。
2. 根据 Network、日志和数据库证据，标出故障最可能所在层。
3. 排列完整数据流，并区分“界面状态变化”和“持久化副作用”。
4. 在沙盒中补齐持久化行为，运行测试。
5. 写一段给 Agent 的修复任务，必须包含复现、预期、边界和验收。
6. 审查 Agent 的交付说明，指出它缺失的证据。
7. 在不同业务表象的变式任务中重新判断。

### 过关标准

- 自动测试证明刷新后数据仍存在。
- 用户能指出此前“成功提示”不能证明数据库写入。
- 给 Agent 的任务描述包含复现步骤、预期结果、真实副作用和至少一个失败路径。
- 零完整答案提示完成主要定位；若使用提示，则记录为 L2 证据并安排复测。
- 变式任务通过后，才产生一次“API/数据流 L3 候选证据”；不能直接把整个技能升为 L3。

## 学习效果验收

第一纵向切片只有满足以下条件才算成立：

1. 同一用户完成前测后，系统能引用原始行为说明当前判断。
2. 用户完成真实沙盒任务，运行结果和数据库副作用被实际验证。
3. 系统区分“独立完成”“提示后完成”和“查看答案后完成”。
4. 用户在变式任务中仍能识别同一原理。
5. 关闭并重新打开应用后，原始尝试、证据和评分理由仍存在。
6. 用户本人确认反馈准确揭示了至少一个此前不知道或说不清的缺口。

第 6 条不能由自动化测试替代；没有真实试玩反馈时，只能标记“工程闭环通过，学习效果待验”。
